# `sc-author` 설계 — 공통 pass (재형식화 + no-op 제거)

[04-design.md](./04-design.md)의 D14–D17을 크기 때문에 나눈 문서. 입력: [03-analysis.md](./03-analysis.md) §4. 검사기 규칙 N1–N4는 [04a-design-checker.md](./04a-design-checker.md).

## 1. 흐름에서의 위치 (C2)

```
Resolve → Load-set → Load → Draft | Audit → [공통 pass] → Neighbors → Check → Hand-off
```

- 공통 pass = 모든 대상 문서에 같은 순서로 적용 (D14)
  1. 재형식화: 고른 형식(04-design §6)으로 옮김 → 문장의 지시 내용은 바꾸지 않음
  2. no-op 후보 수집: 기계(검사기 N1–N4) + 판단(`quality.md` 판정 질문)
  3. 보고 순서: 해로움(03 §3.4) → 기계 후보 → 판단 후보
  4. diff 제시 → 사용자 승인 → 쓰기
- 불변식: 재형식화는 아무것도 지우지 않는다. 문장을 지우는 길은 2–4단계의 승인된 후보뿐

## 2. 유형 처리 (D14)

| 대상 | 공통 pass | 유형별로 더하는 것 |
|---|---|---|
| 알려진 유형 (skill, agent, command, output-style, memory) | 적용 | 기계적 계약만: `fields.yaml`의 위치·필드(F1–F7), 이름 규칙, 길이(S1), `<type>.md` 템플릿 |
| 그 밖의 md 문서 (mode·MCP 가이드, skill 부속 파일, 서브에이전트 프롬프트 파일, auto memory 등) | 적용 | 없음 → `--type generic` (공통 규칙 R·S2·X·N만) |
| 코드 안에 박힌 문구 (hook 주입 문자열 등) | 판단 항목만 | 검사기 미실행 → Hand-off에서 "기계 검사 안 함"이라고 보고 |

- 새 유형을 정의하지 않는다 (D13): 위치·필드라는 기계적 계약이 생길 때만 `fields.yaml`에 행 추가

## 3. Load-set (D15)

Resolve 다음 단계. 03 §2: 같은 문장도 함께 읽히는 문서에 따라 no-op 여부가 달라짐.

- 입력: 대상 경로 + 유형
- 판정: `quality.md` "로드 방식" 표 (03 §2를 사용자 프로젝트용으로 옮김)
  - 항상 로드: CLAUDE.md → `@import` 체인, AGENTS.md(CLAUDE.md 없을 때), `paths:` 없는 rules
  - `paths:` 일치: 같은 경로에 걸리는 rules 전부
  - 서브에이전트: 그 agent 본문만
  - 호출 시 로드: skill 본문 + 본문이 Read하라고 지시한 부속 파일
  - 메모리 색인: 색인 줄은 매 턴, 본문은 열 때만
- 출력: 경로 목록 + 읽는 쪽(Claude | Codex 등) → 사용자에게 한 줄로 보여 줌
- 쓰임
  - 검사기: `--with <path>` 반복 → N3·N4 범위 = 대상 + 목록
  - 판단: 중복·모순·"기본 동작 재진술" 질문의 범위 = 같은 목록
- 집합을 모델이 정하고 검사기는 받기만 한다: 계산 주체를 하나로 둠. 사용자 프로젝트의 로드 경로(import, `paths:`, 다른 하네스)를 검사기가 다 알 수 없음

## 4. 기계 vs 판단 (D16, D17)

| 03 §3 분류 | 처리 | 위치 |
|---|---|---|
| 없어진 대상, 가리키는 곳이 없음 (경로·앵커·`@import`) | 기계 | N1 |
| 실행할 수 없음 (인라인 코드 도구 이름 ↔ agent `tools`) | 기계 | N2 |
| 모순: 같은 항목이 반대 칸에 (정규화 후 같은 문장) | 기계 | N3 |
| 로드 집합 안 중복 (정규화 후 같은 문장) | 기계 | N4 |
| 같은 뜻의 다른 문장 (중복·모순), 산문 속 MCP 서버 이름 | 판단 | `quality.md` |
| 기본 동작 재진술, 막연함, 다른 곳에서 강제, 사실·이유 (03 §3.2) | 판단 | `quality.md` 판정 질문 |
| 끝난 이력·다시 만들 수 있는 값 (메모리) | 판단 | `quality.md` (상태어만으로는 "행동 지침 없음"을 못 가림) |
| 커밋 ID·테스트 이름 확인 | 미룸 | 아래 §6 |

- 경계: 같은 입력에 늘 같은 답이 나오는 것만 검사기. 문장 뜻을 비교해야 하면 `quality.md` (검사기에 섞지 않음)
- 03 표본으로 본 한계: `business-panel-experts.md:51-52`(Ask First ↔ Never)와 `simplicity-guide.md` Context7은 표현이 달라 N2·N3에 안 걸림 → 판단 항목이 잡음. 기계 규칙은 템플릿 복사로 생긴 같은 문장만 잡는다

## 5. `quality.md`에 들어갈 판단 항목 (D17)

- 판정 질문 (03 §3.2, 문장 단위로 판정)
  - 기본 동작 재진술: 하네스·모델이 시키지 않아도 하는가? → 근거는 "모델별 차이"(D12) 행: 모델 ID마다 답이 다를 수 있음
  - 막연함: 관찰 가능한 트리거·대상·임계값이 있는가?
  - 다른 곳에서 강제: 강제 장치가 작성 루프 안에서, 실수 비용 전에 돌고, 고칠 방법을 말하는가? 모두 예일 때만 no-op
  - 사실·이유: 이 사실로 바뀌는 작성 결정이 있는가?
- 남길 것 반례 (03 §3.3): "아니오" 기록, 기본 습관을 뒤집음, 하네스 특이점, 남은 흔적 오해 방지, 근거 위치만 낡음(위치만 고침)
- 해로움 (03 §3.4): 잘못된 작업을 부름, 하지 않은 확인을 했다고 말하게 함, 모순, 출처를 믿게 함 → 보고 맨 앞

제거 근거:
- 기계 후보: 실패한 확인을 그대로 인용 (`path:line: N1 ...`)
- 판단 후보: 판정 질문 + 답 + 근거(하네스 원문, "모델별 차이" 행, A/B 프로브 중 하나) → 승인 전에는 후보일 뿐

## 6. 미룬 것

| 항목 | 이유 | 다시 볼 조건 |
|---|---|---|
| 커밋 ID·테스트 이름 확인 (03 §3.1) | 사용자 저장소의 shallow clone·다른 테스트 러너에서 오탐 | 경로 확인(N1)이 자리 잡은 뒤 요청이 있을 때 |
| 유사 문장 점수(중복·모순) | 임계값이 판단을 숨김 | 판단 항목이 같은 쌍을 반복해서 놓칠 때 |
| 검사기가 load-set을 계산 | §3 마지막 줄 | 모델이 정한 집합의 누락이 관찰될 때 |

## 7. Areas of concern

- N2·N3는 03 표본의 실제 사례(표현이 다른 모순, 산문 속 서버 이름)를 못 잡는다 → 그 몫은 판단 항목. 기계 규칙의 가치는 템플릿 복사로 생긴 같은 문장과 끊긴 경로에 한정
- load-set을 모델이 빠뜨리면 N3·N4가 조용히 통과한다 → Load-set 결과를 사용자에게 보여 주는 것(§3)이 유일한 확인 지점
