# superclaude 개발 흐름 개선안

## 1. 목적과 검토 범위

superclaude의 의도 확인·설계·계획 추적 구조를 유지하면서, 구현 후 리뷰와 검증을 완료 판정까지 일관되게 연결한다.

이번 개선의 목표는 다음과 같다.

- 구현 작업을 끝낸 상태와 사용자 요청을 충족한 상태를 구분한다.
- 구현 후 코드 리뷰가 대표 개발 흐름에서 빠지지 않게 한다.
- 수용 기준마다 실제 검증 증거를 연결한다.
- 계획 경유와 직접 구현에서 동작 변경의 검증 기준을 일치시킨다.
- 변경 규모와 위험에 맞게 절차를 줄이거나 강화한다.

이 문서는 `ajitta/superclaude`의 `stable` 브랜치에서 확인한 명령·규칙을 바탕으로 작성한 개선 제안이다. 실행 성능이나 절차 준수율을 측정한 결과는 아니다. 구현 시점에는 최신 소스와 다시 대조한다.

## 2. 유지할 강점

다음 구조는 유지한다.

- `00-intent.md`에 사용자 의도를 보존하고 후속 단계에서 참조한다.
- 명세 검토와 코드 검토를 구분한다.
- 계획 변경을 `Deviations`에 코드와 함께 기록한다.
- 구현 중 불필요해진 후속 작업은 근거를 남기고 생략할 수 있다.
- 검증 강도는 변경 영향에 따라 결정한다.
- 작은 수정에는 전체 문서화 절차를 적용하지 않는다.

ECC에서는 유효한 RED/GREEN 증거의 정의와 검증 결과의 명시적 기록 방식을 참고한다. 전체 프레임워크, 일률적인 커버리지 목표, 매 단계 체크포인트 커밋까지 도입하지 않는다.

## 3. 현재 흐름의 문제

### 3.1 구현 완료와 기능 완료가 섞여 있다

`/sc:implement --plan`은 마지막 계획 작업이 끝나면 계획과 기능 README를 `complete`로 변경하도록 한다. 그러나 대표 흐름에서는 이후에 `/sc:test`와 `/sc:reflect`를 실행한다.

구현 단계에서도 검증을 수행하므로 무검증 완료라고 볼 수는 없다. 다만 후속 검증과 의도 대조가 남아 있는 시점에 기능 전체가 완료로 표시될 수 있다.

### 3.2 대표 흐름에 구현 후 코드 리뷰가 명시되지 않는다

대형 작업의 대표 흐름에 포함된 앞쪽 `/sc:review`는 명세 검토다. 별도의 브랜치 종료 흐름에는 코드 리뷰가 있지만, 대표 흐름만 따르면 구현 후 코드 리뷰가 빠질 수 있다.

### 3.3 TDD 요구가 진입 경로에 따라 달라진다

`/sc:plan`은 실패 테스트 작성·실패 확인·최소 구현·성공 확인을 작업 템플릿에 포함한다.

반면 직접 `/sc:implement`로 진입하면 같은 RED 증거 요구가 명확하지 않고, `--with-tests`가 별도 옵션으로 존재한다. `/sc:test`도 명시적인 `--tdd` 요청 밖에서는 테스트 케이스를 생성하지 않도록 한다.

동일한 동작 변경인데도 진입 명령에 따라 검증 기준이 달라질 여지가 있다.

## 4. 개선할 개발 흐름

### 4.1 대형·모호한 작업

의도 확인 → 탐색 → 명세 리뷰 → 설계 → 계획 → 구현 → 코드 리뷰 → 필요한 수정 → 최종 검증 → 완료 판정

명세 리뷰와 코드 리뷰는 서로 다른 질문을 다룬다.

| 리뷰 | 질문 |
|---|---|
| 명세 리뷰 | 이 요구와 설계 방향으로 사용자의 문제를 해결할 수 있는가? |
| 코드 리뷰 | 실제 구현이 요구를 충족하며 새로운 결함을 만들지 않았는가? |

기존 명세나 승인된 설계가 있다면 해당 단계를 반복하지 않는다.

### 4.2 작고 명확한 작업

수용 기준 확인 → 필요한 재현·기준선 확인 → 수정 → 영향 범위 검증 → 완료 보고

별도 intent·design·plan 문서를 의무화하지 않는다. 리뷰와 검증 결과도 작업 기록이나 최종 보고에 간결하게 남길 수 있다.

단, 인증·권한·보안·결제·마이그레이션 등은 코드 크기와 관계없이 기존 위험 기반 검증 규칙을 적용한다.

## 5. 완료 상태 정의

기존의 초기 상태 체계는 유지하되, 구현 이후 상태를 다음처럼 구분한다.

| 상태 | 의미 | 진입 조건 |
|---|---|---|
| `implemented` | 합의한 구현 작업을 처리했다 | 계획 작업 처리, 변경 사유 기록, 작업별 검증 결과 기록 |
| `verified` | 현재 구현에 대한 필수 리뷰와 검증을 마쳤다 | 차단 지적 해결, 필요한 검사 통과, 현재 코드에 유효한 증거 확보 |
| `complete` | 합의한 요청의 완료 조건을 충족했다 | 수용 기준과 원래 의도 대조, 잔여 범위 처리 명시 |

작업 체크박스를 모두 체크했다는 이유만으로 기능 전체를 `complete`로 변경하지 않는다.

계획 문서의 작업 진행 상태와 기능 전체의 완료 상태도 구분한다. 같은 `status` 필드를 사용한다면 각 문서에서 무엇의 상태인지 명시해야 한다.

### 상태 재평가

- `verified` 이후 관련 코드가 변경되면 영향을 받는 검증 증거를 다시 평가한다.
- 기존 증거가 변경된 동작을 입증하지 못하면 `implemented`로 되돌린다.
- 모든 변경에서 전체 테스트를 반복하지 않는다. 기존 검증 단계 규칙에 따라 재검증 범위를 정한다.
- 완료 조건 자체가 바뀌면 수용 기준과 범위 변경을 먼저 기록한다.

## 6. 명령별 책임

| 명령 | 책임 | 상태 변경 범위 |
|---|---|---|
| `/sc:plan` | 수용 기준, 구현 작업, 검증 방법을 연결한다 | 계획 진행 상태 |
| `/sc:implement` | 구현, 작업별 검증, 계획 변경 기록을 수행한다 | 기능은 최대 `implemented` |
| `/sc:review` | 의도·명세·코드와 관련 문서를 검토한다 | 리뷰 결과와 지적 기록 |
| `/sc:test` | 필요한 검증을 실행하고 실제 결과를 기록한다 | 검증 결과 기록 |
| `/sc:reflect --type completion` | 수집된 증거로 전체 완료 조건을 판정한다 | 조건 충족 시 `verified`와 `complete` |

`reflect`는 새 테스트를 실행하는 명령으로 바꾸지 않는다. 증거가 부족하면 필요한 검증을 지정하고 해당 단계로 돌려보낸다.

명령을 따로 실행했더라도 같은 완료 기준을 적용한다. 명령 호출 횟수나 순서를 채우는 것 자체를 완료 조건으로 삼지 않는다.

## 7. 수용 기준과 증거 연결

기존 `05-plan.md`의 `Proof` 부분을 확장한다. 별도 증거 문서는 기본적으로 추가하지 않는다.

계획 단계에서는 기준과 검증 방법을 작성하고, 구현·검증 과정에서 실제 결과를 채운다.

| ID | 수용 기준 | 검증 방법 | 결과 | 근거 |
|---|---|---|---|---|
| A1 | 사용자가 요구한 정상 동작 | 테스트 또는 재현 절차 | 미실행 | — |
| A2 | 중요한 실패·경계 조건 | 테스트 또는 실패 주입 | 미실행 | — |
| A3 | 유지해야 하는 기존 동작 | 회귀 테스트 | 미실행 | — |

결과는 `PASS`, `FAIL`, `NOT RUN`, `SKIPPED`로 구분한다.

- `PASS`: 실제 실행 또는 해당 작업에 적합한 검토를 수행했고 기준을 충족했다.
- `FAIL`: 기준을 충족하지 못했다.
- `NOT RUN`: 아직 수행하지 않았다.
- `SKIPPED`: 수행하지 않기로 정했으며 이유와 남는 불확실성을 기록했다.

필수 검증의 `NOT RUN`이나 `SKIPPED`를 `PASS`로 취급하지 않는다. 필수 검증을 수행할 수 없다면 작업을 `implemented`로 남기고 한계를 보고한다. 검증 요구 자체를 변경하려면 이유와 합의 내용을 기록한다.

### 예시: 대용량 내보내기

| ID | 수용 기준 | 검증 방법 |
|---|---|---|
| A1 | 합의한 크기의 요청이 시간 초과 없이 접수된다 | 해당 데이터 크기로 통합 테스트 |
| A2 | 요청자가 자기 결과 파일만 받는다 | 다른 사용자 접근 거부 테스트 |
| A3 | 처리 실패를 사용자가 확인할 수 있다 | 실패 주입 후 상태 확인 |
| A4 | 기존 소규모 내보내기가 유지된다 | 기존 회귀 테스트 |

데이터 크기, 응답 시간, 보존 기간 등의 수치는 요구사항이나 측정으로 정한다. 근거 없는 값을 계획에 넣지 않는다.

## 8. 동작 변경의 검증 기준 통일

`--plan`과 `--with-tests` 사용 여부에 관계없이 동작 변경에는 적절한 증거가 필요하다.

| 변경 종류 | 기본 증거 |
|---|---|
| 버그 수정 | 수정 전 재현 실패 → 수정 후 같은 재현 통과 |
| 새 기능 | 수용 기준에서 도출한 테스트 실패 → 구현 후 통과 |
| 리팩터링 | 필요한 기존 동작을 확인하는 테스트의 변경 전후 통과 |
| 문서·주석 수정 | 정적 검토, 해당 문서를 읽는 도구가 있으면 관련 검사 |
| 자동 테스트가 어려운 변경 | 재현 명령·수동 확인·관측 결과와 검증 한계 |

### 유효한 RED 조건

다음을 모두 만족해야 RED 증거로 인정한다.

1. 대상 테스트나 재현 절차가 실제 실행됐다.
2. 의도한 변경 대상 때문에 실패했다.
3. 의존성 누락이나 무관한 설정 오류만으로 실패한 것이 아니다.

테스트를 작성했지만 실행하지 않은 상태는 RED가 아니다.

수정 후에는 같은 동작을 확인하는 절차로 GREEN을 확인한다. 통과시키기 위해 기대 결과를 변경했다면, 그 변경이 원래 수용 기준에 맞는지 별도로 검토한다.

자동 테스트가 부적절한 경우에는 대체 증거와 이유를 기록한다. 형식적인 테스트를 추가하는 것으로 대체하지 않는다.

## 9. 구현 후 리뷰와 재검증

코드 리뷰는 다음을 확인한다.

- 원래 의도와 수용 기준을 충족하는가?
- 요구하지 않은 변경이나 인접 리팩터링이 들어갔는가?
- 테스트가 실제 결함과 중요한 경계 조건을 다루는가?
- 계획 변경과 체크박스가 실제 코드와 일치하는가?
- 변경으로 인해 상시 로드 문서가 틀려지지 않았는가?

지적은 근거로 확인하고, 근거가 없으면 철회하거나 제안 수준으로 낮춘다.

차단 여부는 심각도 이름만으로 판단하지 않는다. 각 지적에 다음을 명시한다.

- 어떤 수용 기준이나 정확성·보안 조건을 위반하는가?
- 완료 전에 반드시 해결해야 하는가?
- 제안이나 후속 작업으로 남겨도 되는가?

리뷰 후 코드를 수정했다면 영향받는 검증을 다시 실행한다. 현재 동작을 입증하지 못하는 수정 전 결과를 최종 통과 증거로 재사용하지 않는다.

## 10. 완료 판정

`/sc:reflect --type completion`은 다음을 확인한다.

- 원래 의도의 각 항목이 결과에 반영됐는가?
- 수용 기준마다 유효한 증거가 있는가?
- 필수 검증에 실패·미실행 항목이 남았는가?
- 리뷰의 미해결 차단 지적이 있는가?
- 관련 코드 변경으로 오래된 증거가 생기지 않았는가?
- 계획에서 제외하거나 변경한 작업에 이유가 있는가?
- 남은 작업과 이번 요청의 범위가 구분됐는가?

배포가 요청 범위에 포함됐다면 배포까지 완료 조건에 넣는다. 개발만 요청됐다면 임의로 운영 배포까지 범위를 넓히지 않는다.

완료 보고는 다음 형식으로 간결하게 남긴다.

- 결과: 무엇을 구현했는가?
- 검증: 무엇을 실행했고 어떤 결과였는가?
- 의도 대조: 합의한 완료 조건을 충족했는가?
- 잔여 범위: 확인하지 못했거나 별도로 남긴 것은 무엇인가?
- 상태: `implemented`, `verified`, `complete` 중 무엇인가?

## 11. 수정 대상

| 파일 | 변경 내용 |
|---|---|
| `src/superclaude/commands/plan.md` | 수용 기준과 증거 표를 기존 Proof 부분에 연결 |
| `src/superclaude/commands/implement.md` | 구현 후 기능 상태를 최대 `implemented`로 제한하고 직접 구현의 증거 기준 명시 |
| `src/superclaude/commands/review.md` | 차단 지적의 기준과 구현 후 리뷰 결과 기록 명확화 |
| `src/superclaude/commands/test.md` | 검증 결과 구분과 수정 후 재검증 규칙 정합성 확보 |
| `src/superclaude/commands/reflect.md` | 완료 판정 조건과 상태 전환 책임 명시 |
| `src/superclaude/core/rules/RULES_QUALITY.md` | 공통 완료·검증 계약 정의, 기존 검증 단계 규칙과 연결 |
| `README.md` | 대표 흐름에 구현 후 리뷰 추가, 상태와 소규모 작업 예외 설명 |

공통 규칙을 여러 명령에 복제하지 않는다. 공통 계약은 품질 규칙에 두고 각 명령은 자기 책임과 참조만 명시한다.

## 12. 도입 순서와 확인 기준

### 1단계: 문서 계약 정리

상태 정의, 명령별 책임, 대표 흐름을 수정한다.

기존 구조·교차 참조 검사를 확인하고 변경에 해당하는 검사를 실행한다. 실제로 검사하지 않은 항목을 통과했다고 보고하지 않는다.

### 2단계: 대표 사례로 흐름 점검

다음 사례를 따라가며 절차의 누락과 과잉을 확인한다.

| 사례 | 확인할 동작 |
|---|---|
| 문서 오탈자 수정 | 불필요한 계획·테스트·승인을 요구하지 않는다 |
| 단일 파일 버그 수정 | 재현과 수정 효과를 입증한다 |
| 명확한 기능 구현 | 수용 기준·구현·리뷰·검증이 연결된다 |
| 모호한 대형 기능 | 원래 의도가 후속 단계까지 추적된다 |
| 인증 관련 작은 변경 | 크기가 작아도 강화된 검증을 적용한다 |
| 리뷰 후 코드 수정 | 관련 증거를 재검증한다 |
| 필수 검증 환경 부재 | `complete`로 선언하지 않고 한계를 보고한다 |

문서만 따라간 점검과 실제 실행 결과는 구분한다.

### 3단계: 필요한 부분만 자동화

초기에는 상태 검사 스크립트나 새로운 훅을 추가하지 않는다.

실제 작업에서 잘못된 완료 선언이나 상태 누락이 반복되면, 어떤 조건을 기계적으로 판정할 수 있는지 확인한 뒤 최소한의 검사를 추가한다. 의도 충족 같은 의미 판단까지 단순한 파일·문자열 검사로 보장한다고 주장하지 않는다.

## 13. 개선 완료 기준

- 구현 작업 종료만으로 기능이 `complete`가 되지 않는다.
- 대표 흐름에서 명세 리뷰와 코드 리뷰가 구분된다.
- 수용 기준마다 증거 또는 명시적인 미검증 사유가 남는다.
- 직접 구현과 계획 경유 구현의 동작 검증 기준이 일치한다.
- 코드 수정 후 필요한 재검증이 연결된다.
- 필수 검증 실패나 미해결 차단 지적이 완료 판정에 반영된다.
- 작은 수정에는 불필요한 문서와 승인 단계가 추가되지 않는다.
- 모델이 따르는 절차와 훅이 실제로 강제하는 조건이 구분되어 설명된다.
