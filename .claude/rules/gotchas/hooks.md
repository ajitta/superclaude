# Project Gotchas — Hook Scripts & Path Resolution
# Last reviewed: 2026-09-05
# Python runtime traps in hook scripts + CLI. Content-authoring traps live in authoring.md.

- script-needs-console-entry: A script under `scripts/` that imports `superclaude.*` is runnable ONLY by the installer's interpreter. `~/.claude/superclaude/` ships content (core/ mcp/ modes/ templates/), never the package, so a copied `python3 X.py` raises ModuleNotFoundError; hooks never hit it because they run `superclaude hook <name>` (`cli/hook_dispatch.py`), the same console script, from inside the installed package — no substitution reaches command markdown either. Any script with BOTH a hook path and a human path needs a console subcommand (`superclaude insight` forwards argv to `insight_writer.main(argv, prog=...)`) — documenting a file path is the bug. Measured 2026-08-29: `/sc:insight --review` prescribed bare `python3` for months and failed on every manual run; fix `superclaude insight` + drift-guard test that the command doc never re-prescribes `python3`.

- hook-path-scope: Hook scripts + hook-imported modules resolve `.claude` paths via `superclaude.utils` resolvers — `project_root()`, `claude_base()`, `hook_state_dir()`. `Path.home() / ".claude"` and `Path.cwd() / ".claude"` in that position are the bug, not the baseline: hook CWD is NOT guaranteed to be the project root (CC documented behavior), and hardcoded `$HOME` makes a local/project-scope install write state where `superclaude uninstall` cannot reach it. Three instances found 2026-07-25 (`context_loader`, `context_reset` + `hook_tracker`/`mcp_fallback`, `get_skill_directories`); commit `52b5517`. Symptom of the CWD variant is silent: from a subdirectory the skills banner reported 9 skills instead of 22 and the token estimate 55612 instead of 94011 — no error, just wrong scope.
- worktree-anchor-split: In a linked git worktree the two anchors disagree — CC reads the settings file that registered the hook from the MAIN worktree (canonical git root, `findCanonicalGitRoot`) but sets `$CLAUDE_PROJECT_DIR` to the LINKED one. Measured 2026-09-05 in an Orca worktree of this repo: all 14 local-scope hooks failed with `can't open file '<worktree>/.claude/superclaude/scripts/*.py'` while the install sat in the main checkout, and `~/.claude.json` held a project entry only for the main root. Two consequences, one loud and one silent: a `$CLAUDE_PROJECT_DIR`-built hook command misses by a whole directory, AND `claude_base()` — which probes `<project>/.claude/superclaude` — fell straight through to `~/.claude`, so content and hook state resolved to a scope holding no install at all. Fixed by (a) hook commands carrying no path at all — `superclaude hook <name>` since 2026-09-05; the interim fix had every scope but `project` bake an absolute scripts path — and (b) `utils.main_worktree_root()` giving `claude_base()` a main-worktree hop before user scope. `project_root()` deliberately still names the linked worktree — code and content follow the install, per-project data follows the session, and `project_key()` keeps worktrees from colliding in the shared state dir. **The (b) hop rests on undocumented CC behavior.** That CC resolves the project — and therefore its settings file — to the canonical git root was established empirically here (`findCanonicalGitRoot` in the 2.1.261 binary; `~/.claude.json` holding a project entry for the main root only, no trust dialog for the worktree), not from any published contract. If a future CC reads settings from the linked worktree instead, `claude_base()` will point at the wrong install and, as before, do it silently. Re-check this the next time worktree hooks misbehave rather than assuming the anchor still holds.
- git-common-dir-paths: In a linked worktree git resolves `info/exclude` — and `hooks/`, `objects/`, most of `refs/` — through the COMMON dir (`<gitdir>/commondir`, relative or absolute); `.git/worktrees/<name>/` holds the per-worktree set (HEAD, index, config.worktree, logs/HEAD, `info/sparse-checkout`, `refs/bisect`, gitdir, commondir …). Per-file, not per-directory: `info/exclude` is common while `info/sparse-checkout` is per-worktree (both measured with `git rev-parse --git-path`, git 2.55). So `<gitdir>/info/exclude` is a file nothing reads — `install_git_exclude` wrote there from its first worktree support until 2026-09-05 and two tests pinned it (measured git 2.55: pattern in the per-worktree file → `check-ignore` exit 1; in the common file → match). Rule: any per-worktree gitdir path that is not on git's per-worktree list needs `git rev-parse --git-path <p>` checked once in a real `git worktree add` repo, not a hand-built fixture — the fixture had no `commondir` file because the author did not know git writes one. A `.git` pointer file WITHOUT `commondir` is a submodule; there the gitdir itself is complete.
- cli-vs-hook-cwd: Counterpart of the above — do NOT apply `project_root()` inside `cli/` modules. `install_paths.py:39` `Path.cwd() / ".claude"` is correct: the user types `superclaude install --scope local` from the project root, and `CLAUDE_PROJECT_DIR` exists only inside a CC session, so the resolver would make the CLI behave differently inside vs outside Claude Code. Hook code follows the install; CLI code follows the user's shell.
- runtime-path-two-classes: Every runtime path goes through `superclaude.utils` — `project_root()`, `claude_base()`, `hook_state_dir()`, `project_key()`. Two classes, opposite lifetimes: ephemeral machine state (context cache, hook tracker, MCP fallback log, loop_guard counters) under `hook_state_dir()` so uninstall removes it; durable user data (`insights.jsonl`) under `project_root()/".claude"` so uninstall preserves it. Deciding per-writer is what produced four wrong call sites out of eight. State that is not session-keyed needs `project_key()` in its filename — a user-scope install shares one `hook_state_dir()` across every project. When auditing for violations, enumerate every script reachable from `hooks.json`, not every script touching `.claude/`: `memory_staleness.py` was missed on the first pass because it anchors CC's own `~/.claude/projects/<encoded-root>/` and so fell outside a `.claude`-shaped grep.
- test-anchor-env: Tests that exercise these resolvers must `monkeypatch.setenv("CLAUDE_PROJECT_DIR", str(tmp_path))`, not just `monkeypatch.chdir(tmp_path)` — `project_root()` reads the env first, so chdir alone lets the test write into the real repo or real `~/.claude`. For `claude_base()`, also `mkdir` a `<tmp>/.claude/superclaude` marker, or it falls back to the developer's home. Measured 2026-07-25: 19 stray `loop_guard_*.json` in real `~/.claude/.superclaude_hooks/` and 33 fixture lines appended to the repo's real `insights.jsonl` before the fixtures were pinned.
- hook-runtime-state-uninstall: New runtime state written by a hook goes under `claude_base()` so `uninstall_all()` reaches it — step 5a unlinks files, 5b rmtree's directories (`install_inventory.py`). State placed outside `base_path` survives uninstall silently and is invisible to `--list-all`.
- hook-upgrade-live-session: Do not delete `<base>/superclaude/scripts/` (pre-console-entry script copies) from install code. The first premise here — "CC snapshots hook commands at session start" — is FALSE for CC 2.1.x: measured 2026-09-05, after `install --force --scope local` rewrote settings.local.json the SAME live session's PreToolUse/PostToolUse hooks ran the new `superclaude hook …` commands. The copies still matter for a registration a non-force install left in legacy form (a retired hook) and for any CC that does snapshot, and python's "can't open file" is exit 2 = PreToolUse/Stop BLOCK — every tool call blocked. `install_hooks()` prints an ℹ️ line naming the dir instead, and the line is state-aware: a non-force install rewrites legacy `<python> …/<name>.py` commands to `superclaude hook <name>` (matcher/timeout kept), so the notice says "remove after restart" only when no registration still names the copies, else "do not remove; --force rewrites". Same mechanism means a `make sync-local` inside a running session is safe only BECAUSE the copies stay. Second coupling, new with the console entry: `make deploy` is an EDITABLE uv tool and the venv is active in the launching shell, so this working tree IS the live hook code for every session on the machine (see editable-tool-branch-switch).
- hook-path-inherits-launch-shell: CC's hook shell inherits the launching shell's PATH — measured 2026-09-05 by dumping `os.environ` from the PreToolUse Bash hook (VS Code terminal → `zsh -il` → claude): PATH carried `~/.local/bin` (where uv/pipx and CC's own native installer live) plus the active `.venv/bin`, and `which superclaude` resolved. The installer's ⚠️ and doctor's "superclaude on PATH" read `install_paths.probe_console_script()`: this process's PATH MINUS the running interpreter's own bin (under `uv run` that is `.venv/bin`, which a bare `shutil.which` always found even with an empty PATH, so the warning could never fire from `make sync-*`), then `<found> hook --help` and `--version` — whichever `superclaude` PATH resolves is the package whose hooks run, not necessarily the one that wrote settings.json. The installer's shell PATH is read as a proxy for the hook shell's, and only a virtualenv's own bin is left out (`sys.prefix != sys.base_prefix`; a system or python.org interpreter's scripts dir is the user's permanent PATH entry): a CC launched from a GUI with a narrower PATH can still fail with 127 while doctor passes, and WINDOWS WAS NEVER MEASURED (the request named it; `%USERPROFILE%\.local\bin` on the hook shell's PATH and `superclaude.exe` resolution are inferred from uv docs only). Symptom of a wrong PATH: hooks silently absent (no SessionStart banner, no context injection). Diagnose from inside CC: `! which superclaude`.
- hook-fast-path-no-click: `superclaude hook` must never import click, yaml or `superclaude.cli.main` — `cli/entry.py` dispatches `hook` before the click app loads because `import superclaude.cli.main` ≈ 40ms vs ≈ 20ms for a whole hook run (measured 2026-09-05), × 3 spawns per Bash call. `tests/unit/test_hook_dispatch.py` asserts the import graph in a subprocess; a click import added to `hook_dispatch.py` (or an eager `from .main import main` back in `cli/__init__.py`) is a silent 2× hook-latency regression no wall-clock test flags. Shim regen: a changed `[project.scripts]` target only reaches `.venv/bin/superclaude` / `~/.local/bin/superclaude` after `uv pip install -e ".[dev]"` / `make deploy`; a stale shim still works via the click `hook` command, just without the fast path.
- editable-tool-branch-switch: Locked myself out on 2026-09-05. `git checkout master` (no `cli/entry.py` yet) followed by `uv run pytest` re-synced `.venv/bin/superclaude` from master's pyproject to the click `main:main` shim; the hook shell has `.venv/bin` first (venv active in the launching shell), so `superclaude hook loop_guard` → click "No such command 'hook'" → exit 2 → EVERY Bash/Read/Edit/Write in the live session blocked by PreToolUse — including the command that would have fixed it. Rules: (a) merge with `git checkout master && git merge --no-ff <branch>` in ONE command and run no `uv run`/`make` while the checked-out tree lacks the console entry; (b) `git merge -F -` does not read stdin — use `-m "$(cat <<'EOF' … EOF)"` — that failure is what left master unmerged; (c) recovery from inside CC needs a tool the `Bash` matcher does not gate (Monitor runs a shell script under tool name `Monitor`) or the user's `! <cmd>`; (d) the same exit-2 lockout awaits any teammate whose PATH-first `superclaude` predates the `hook` subcommand — the doctor/installer probe (`hook --help` + version) is the early warning.
