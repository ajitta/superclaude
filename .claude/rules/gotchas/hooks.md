# Project Gotchas — Hook Scripts & Path Resolution
# Last reviewed: 2026-10-07
# Python runtime traps in hook scripts + CLI. Content-authoring traps live in authoring.md.

- script-needs-console-entry: `~/.claude/superclaude/` ships content, not the package — `python3 X.py` on a script importing `superclaude.*` → ModuleNotFoundError. A script with a human path (hooks use `superclaude hook <name>`) needs a console subcommand (`superclaude insight`); documenting a file path is the bug.

- hook-path-scope: Hook scripts and their imports resolve `.claude` via `superclaude.utils` (`project_root()`, `claude_base()`, `hook_state_dir()`); `Path.home()`/`Path.cwd()` there is the bug. Hook CWD ≠ project root (CC documented) → silent wrong scope; `$HOME` puts local-scope state where uninstall cannot reach.
- worktree-anchor-split: Linked worktree: CC reads settings from the MAIN worktree but sets `$CLAUDE_PROJECT_DIR` to the LINKED one (2026-09-05: `claude_base()` fell silent to `~/.claude`). Fix: path-free `superclaude hook <name>` + `utils.main_worktree_root()` hop; `project_root()` keeps the linked one by design.
- worktree-anchor-undocumented: `main_worktree_root()` rests on unpublished behavior (`findCanonicalGitRoot`, 2.1.261: settings resolve to the canonical root). If CC ever anchors on the linked tree, `claude_base()` picks the wrong install. Worktree hooks misbehave? Check: does `~/.claude.json` list only the MAIN root?
- git-common-dir-paths: Linked worktree: git reads `info/exclude`, hooks/, objects/, refs/heads via `<gitdir>/commondir`, per-file: HEAD, index, `info/sparse-checkout`, refs/bisect stay per-worktree. A `.git` file WITHOUT `commondir` = submodule. Verify via `git rev-parse --git-path <p>`; fixtures need `commondir`.
- cli-vs-hook-cwd: Do NOT use `project_root()` inside `cli/`. `install_paths.py`'s `Path.cwd()/.claude` branch is correct: the user runs `superclaude install --scope local` from the project root, and `CLAUDE_PROJECT_DIR` exists only inside a CC session. Hook code follows the install; CLI code follows the user's shell.
- runtime-path-two-classes: Two lifetimes: ephemeral state → `hook_state_dir()` so uninstall removes it; durable user data (`insights.jsonl`) → `project_root()/.claude` so uninstall keeps it. Non-session-keyed state needs `project_key()` in its filename — user scope shares one dir across projects.
- runtime-path-audit-scope: When auditing path resolution, enumerate every script reachable from `hooks.json`, not every file a `.claude` grep hits — `memory_staleness.py` anchors CC's own `~/.claude/projects/<encoded-root>/` and was missed on the first pass.
- test-anchor-env: Resolver tests must `monkeypatch.setenv("CLAUDE_PROJECT_DIR", str(tmp_path))` — `project_root()` reads the env first, so `chdir` alone writes into the real repo or `~/.claude`. For `claude_base()` also `mkdir <tmp>/.claude/superclaude`, else it falls back to the developer's home.
- hook-runtime-state-uninstall: New hook runtime state goes under `hook_state_dir()` so `uninstall_all()` reaches it (`install_inventory.py` step 5a rmtree's it). State outside `base_path` survives uninstall silently and is invisible to `--list-all`.
- hook-upgrade-live-session: Install code never deletes `<base>/superclaude/scripts/`: a legacy `<python> …/<name>.py` registration still runs those copies; "can't open file" = exit 2 = PreToolUse/Stop BLOCK. Non-force install rewrites legacy registrations; its ℹ️ says keep (still referenced) or remove after restart.
- hook-commands-not-snapshotted: CC 2.1.x picked up rewritten hook commands mid-session (observed 2026-09-05, version-dependent), so `make sync-local` mid-session is safe only because the legacy copies stay. Editable-tool coupling: editable-tool-branch-switch.
- hook-path-inherits-launch-shell: The hook shell inherits the launching shell's PATH (zsh, 2026-09-05): whichever `superclaude` PATH resolves runs the hooks, not necessarily the package that wrote settings.json. Symptom: hooks silently absent (no SessionStart banner). Diagnose inside CC: `! which superclaude`.
- doctor-path-probe-is-proxy: Doctor's PATH check and installer ⚠️ use `install_paths.probe_console_script()`: own PATH minus the active venv bin (under `uv run` which() always hits it), then `hook --help`: a hook-shell proxy. GUI-launched CC with a narrower PATH can exit 127 while doctor passes; Windows unmeasured.
- hook-fast-path-no-click: `superclaude hook` never imports click/yaml/`superclaude.cli.main`: `cli/entry.py` dispatches `hook` before the click app loads (click ≈ 40ms vs ≈ 20ms whole hook run, × 3 per Bash call). `tests/unit/test_hook_dispatch.py` pins the import graph; a click import there = silent 2× regression.
- console-shim-regen: A changed `[project.scripts]` target reaches `.venv/bin/superclaude` / `~/.local/bin/superclaude` only after `uv pip install -e ".[dev]"` / `make deploy`; a stale shim still works via the click `hook` command, just without the fast path.
- editable-tool-branch-switch: This tree is the live hook code: `.venv/bin` shim (venv active at launch) or `make deploy`'s editable tool. `uv run`/`make` on a tree lacking `cli/entry.py` re-syncs that shim to click `main:main` → `superclaude hook` "No such command" → exit 2 → every gated tool blocked (2026-09-05).
- merge-without-uv-run: Merge in ONE command — `git checkout master && git merge --no-ff <branch> -m "$(cat <<'EOF' … EOF)"` (`-F -` ignores stdin), no `uv run`/`make` on a tree w/o `cli/entry.py`. Recover via Monitor or `! <cmd>`. A PATH-first `superclaude` predating `hook` hits the same lockout; doctor warns.
