# Project Gotchas — Hook Scripts & Path Resolution
# Last reviewed: 2026-08-29
# Python runtime traps in hook scripts + CLI. Content-authoring traps live in authoring.md.

- script-needs-console-entry: A script under `scripts/` that imports `superclaude.*` is runnable ONLY by the installer's interpreter. `~/.claude/superclaude/` ships content (core/ mcp/ modes/ scripts/ templates/), never the package, so `python3 ~/.claude/superclaude/scripts/X.py` raises ModuleNotFoundError; hooks never hit it because `install_components.py:392` bakes `sys.executable` as `{{PYTHON_BIN}}`, and that substitution runs for hooks.json + skills only, never for command markdown. Any script with BOTH a hook path and a human path needs a console subcommand (`superclaude insight` forwards argv to `insight_writer.main(argv, prog=...)`) — documenting a file path is the bug. Measured 2026-08-29: `/sc:insight --review` prescribed bare `python3` for months and failed on every manual run; fix `superclaude insight` + drift-guard test that the command doc never re-prescribes `python3`.

- hook-path-scope: Hook scripts + hook-imported modules resolve `.claude` paths via `superclaude.utils` resolvers — `project_root()`, `claude_base()`, `hook_state_dir()`. `Path.home() / ".claude"` and `Path.cwd() / ".claude"` in that position are the bug, not the baseline: hook CWD is NOT guaranteed to be the project root (CC documented behavior), and hardcoded `$HOME` makes a local/project-scope install write state where `superclaude uninstall` cannot reach it. Three instances found 2026-07-25 (`context_loader`, `context_reset` + `hook_tracker`/`mcp_fallback`, `get_skill_directories`); commit `52b5517`. Symptom of the CWD variant is silent: from a subdirectory the skills banner reported 9 skills instead of 22 and the token estimate 55612 instead of 94011 — no error, just wrong scope.
- worktree-anchor-split: In a linked git worktree the two anchors disagree — CC reads the settings file that registered the hook from the MAIN worktree (canonical git root, `findCanonicalGitRoot`) but sets `$CLAUDE_PROJECT_DIR` to the LINKED one. Measured 2026-09-05 in an Orca worktree of this repo: all 14 local-scope hooks failed with `can't open file '<worktree>/.claude/superclaude/scripts/*.py'` while the install sat in the main checkout, and `~/.claude.json` held a project entry only for the main root. Two consequences, one loud and one silent: a `$CLAUDE_PROJECT_DIR`-built hook command misses by a whole directory, AND `claude_base()` — which probes `<project>/.claude/superclaude` — fell straight through to `~/.claude`, so content and hook state resolved to a scope holding no install at all. Fixed by (a) every scope but `project` baking an absolute scripts path (`install_components.py`; only project's settings.json is shared, so only it pays for portability) and (b) `utils.main_worktree_root()` giving `claude_base()` a main-worktree hop before user scope. `project_root()` deliberately still names the linked worktree — code and content follow the install, per-project data follows the session, and `project_key()` keeps worktrees from colliding in the shared state dir. **The (b) hop rests on undocumented CC behavior.** That CC resolves the project — and therefore its settings file — to the canonical git root was established empirically here (`findCanonicalGitRoot` in the 2.1.261 binary; `~/.claude.json` holding a project entry for the main root only, no trust dialog for the worktree), not from any published contract. If a future CC reads settings from the linked worktree instead, `claude_base()` will point at the wrong install and, as before, do it silently. Re-check this the next time worktree hooks misbehave rather than assuming the anchor still holds.
- cli-vs-hook-cwd: Counterpart of the above — do NOT apply `project_root()` inside `cli/` modules. `install_paths.py:39` `Path.cwd() / ".claude"` is correct: the user types `superclaude install --scope local` from the project root, and `CLAUDE_PROJECT_DIR` exists only inside a CC session, so the resolver would make the CLI behave differently inside vs outside Claude Code. Hook code follows the install; CLI code follows the user's shell.
- runtime-path-two-classes: Every runtime path goes through `superclaude.utils` — `project_root()`, `claude_base()`, `hook_state_dir()`, `project_key()`. Two classes, opposite lifetimes: ephemeral machine state (context cache, hook tracker, MCP fallback log, loop_guard counters) under `hook_state_dir()` so uninstall removes it; durable user data (`insights.jsonl`) under `project_root()/".claude"` so uninstall preserves it. Deciding per-writer is what produced four wrong call sites out of eight. State that is not session-keyed needs `project_key()` in its filename — a user-scope install shares one `hook_state_dir()` across every project. When auditing for violations, enumerate every script reachable from `hooks.json`, not every script touching `.claude/`: `memory_staleness.py` was missed on the first pass because it anchors CC's own `~/.claude/projects/<encoded-root>/` and so fell outside a `.claude`-shaped grep.
- test-anchor-env: Tests that exercise these resolvers must `monkeypatch.setenv("CLAUDE_PROJECT_DIR", str(tmp_path))`, not just `monkeypatch.chdir(tmp_path)` — `project_root()` reads the env first, so chdir alone lets the test write into the real repo or real `~/.claude`. For `claude_base()`, also `mkdir` a `<tmp>/.claude/superclaude` marker, or it falls back to the developer's home. Measured 2026-07-25: 19 stray `loop_guard_*.json` in real `~/.claude/.superclaude_hooks/` and 33 fixture lines appended to the repo's real `insights.jsonl` before the fixtures were pinned.
- hook-runtime-state-uninstall: New runtime state written by a hook goes under `claude_base()` so `uninstall_all()` reaches it — step 5a unlinks files, 5b rmtree's directories (`install_inventory.py`). State placed outside `base_path` survives uninstall silently and is invisible to `--list-all`.
